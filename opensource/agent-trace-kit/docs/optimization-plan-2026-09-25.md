## F1：未知 Run 不能被当作已确认的共同执行范围

**证据。** [scopeKey](../src/events.js#L96) 把缺失的 run ID 变成 `null`；[运行分组](../src/model.js#L102) 继续把相同空范围的事件分到一个组；[父节点匹配](../src/model.js#L73) 在这个组内解析父子边，[运行结果](../src/model.js#L105) 继续采信终态。相比之下，[工具关联](../src/tools.js#L32) 已明确禁止缺失 run ID 的配对，两种视图的证据门槛不一致。

**本地复现。** 三条合成事件都不带 run ID：父 Agent 启动、带父引用的子 Agent 启动、`complete + success:true`。当前结果为 `runId:null`、1 条 `parent` 边、`outcome:succeeded`；仅在旁边附上三条 `missing_run_id` 警告。

**影响。** 拼接旧日志或接入未携带 run ID 的生产者时，用户无法确认这些事件来自同一次运行，但图和汇总仍给出确定关系/成功状态。这里并不是已经证明真实发生了跨任务合并，而是无法排除这种合并时仍给出确定结论。

**建议。** 保留未知范围的事件供查看，但把它标成未归属事件集合，不给出确定的运行级成功或跨事件父子边。单条生产者的成功声明可以保留为原始证据，不能升级为该集合的共同终态。调用者若确实掌握运行范围，可显式提供范围上下文；不要用随机 ID 或文件名自动伪造真实执行身份。

**验收标准。**

- 上述三事件样例保留全部事件和诊断，但运行级结果为 `unknown`，不产生确定 `parent` 边。
- 工具、关系、终态对缺失范围采用同一政策。
- 显式不同 workspace/session/run 仍隔离；已知范围的正常父子图不回退。
- 增加无 run ID、多个未知范围片段、显式范围补充的回归；不破坏现有 [不同 run 父节点测试](../test/model.test.js#L34)。

**可行性与投入。** 0.5–1 工程日。变更集中在模型层和测试，不涉及日志迁移、付费服务或自动执行。

## F2：规范化后仍把字段存放位置当成语义冲突

**证据。** [字段读取](../src/events.js#L50) 支持根字段与 `data` 别名；[第 88 行](../src/events.js#L88) 又完整保留 `data`；[指纹](../src/events.js#L120) 对整个规范化对象序列化。等价身份/工具字段搬到不同位置后，保留下来的冗余别名仍使指纹不同。[第 123 行](../src/events.js#L123) 的重放比较只记住首次签名，导致冲突版本自己的重复记录不一定计入 duplicates。

**本地复现。**

- 两条相同事件身份、时间、摘要、参数的 `tool_call`：第一条把 agent/task/tool/call ID 放根上，第二条放入支持的 `data` 别名。两条都能单独规范化，但一起收集得到 `accepted:0`、`conflictingIdentities:1`。
- 同一身份的两个冲突版本 A/B：`[A,B,B]` 的 `duplicates` 是 0；相同多重集合换成 `[B,B,A]` 后是 1。两者都应继续隔离冲突，重放计数不应依赖先到哪个版本。

**影响。** 同一事件经过不同适配器、流式接收和存档转换后，本来可合并的记录被一起排除。重放统计也可能因传输排序而改变，使排障与输入质量统计不稳定。

**建议。** 明确一个规范化语义投影：已提升且值相同的已知别名只参与一次指纹，未知扩展字段及真实工具参数仍参与冲突判断。保留原始字段供诊断，不靠无差别删掉 `data` 来“解决”冲突。对已隔离身份记录每个已见版本的签名，以稳定统计重复，任何版本都不得重新恢复成可信事件。

**验收标准。**

- 等价根字段/别名样例得到 1 个有效事件、1 次重复、0 个冲突。
- 根/别名值真正不一致仍被拒绝；修改工具参数仍导致隔离，不能掩盖实质差异。
- A/B 及各自重复的任意排列具有一致的 accepted/duplicates/conflictingIdentities。
- 保留 [属性顺序等价与冲突隔离](../test/events.test.js#L56) 的保证，并补当前缺失的字段布局等价断言。

**可行性与投入。** 0.5–1.5 工程日。技术可行性高；实施前需明确哪些字段是已知别名，不能把所有同名扩展字段都视为重复元数据。

## F3：互相矛盾的成功与费用声明需要可见诊断

**证据。** [终态解释](../src/model.js#L9) 处理了取消、中断和 `failed`，但 `status:'blocked'` 与 `data.success:true` 同时出现时仍返回 `succeeded`。[费用读取](../src/model.js#L106) 对根 `cost` 和 `data.totalCost` 使用优先取值，没有校验二者冲突。[工具结果解释](../src/tools.js#L4) 也需要同一套一致性约定，避免各处规则漂移。

**本地复现。** 一条合法格式的 `complete` 带 `status:'blocked'`、`data.success:true`、`cost:1`、`data.totalCost:2`。当前结果为 `succeeded`、记录费用 1、`issues:[]`。

**影响。** 消费者会看到无警告的成功和单一金额，不知道原始证据互相矛盾。这不代表发生了账单错误或权限绕过，问题在于分析结果对冲突记录表现得过于确定。

**建议。** 为已识别状态和费用候选增加一致性检查，保留候选值及事件定位。阻断与成功互相冲突时给出保守结果和明确诊断，不仅按字段优先级吞掉另一方。两个运行总额冲突时返回未知金额，而不是擅自选择、相加或平均。继续区分运行记录费用与真实账单，不能引入模型核对来解决这种确定性检查。

**验收标准。**

- 冲突样例不得无诊断地显示 `succeeded`；记录 `conflicting_outcome` 或同等可读诊断。
- 根费用 1 与候选总额 2 时，费用为 `null` 并展示冲突原因；相同值 0/0 正常保留为 0。
- 缺少金额仍保持未知，Agent 费用不能再次累计到运行总额。
- 覆盖 blocked/success、failed/success、中断/success 组合；不破坏 [负面终态优先](../test/model.test.js#L54) 与 [缺失用量](../test/model.test.js#L71) 的现有规则。

**可行性与投入。** 0.5–1 工程日。全部是本地确定性判断；先固定输出约定，再统一运行与工具结果解释。

## F4：给接入方一个不会丢掉输入诊断的组合入口

**证据。** [readTraceFile](../src/jsonl.js#L70) 把输入错误、去重计数与剩余事件分开返回；[summarizeTrace](../src/model.js#L118) 只接受事件并重新统计。[中文示例](../README.md#L74) 与 [英文示例](../README_EN.md#L74) 都把 `trace.events` 继续交给 model/index/summary，而没有传递 `trace.issues` 与原始计数。[类型声明](../src/index.d.ts#L34) 已有 `CollectedTrace`，但高层分析入口没有消费它。

**本地复现。** 合成输入包含一个有效完成事件、一个格式错误事件。`collectEvents` 得到 `invalid:1`、1 条错误；按示例把其 `events` 交给 `summarizeTrace` 后，变成 `invalid:0`、0 条错误。JSONL 的源码路径同样返回这种拆分结果；本轮用内存等价路径复现，没有写入测试日志。

**影响。** 接入者照抄示例，很容易把“去掉问题记录后的集合”当成完整干净输入。被隔离的冲突、坏行和首次诊断不会自动恢复。注意：当前 CLI 自己拼回了 `loaded.issues`，本发现不是说 CLI 的错误退出码已失效。

**建议。** 增加一个小型组合入口，例如接收完整 `CollectedTrace` 的分析函数或 `analyzeTraceFile`，统一返回原始 counts/issues、选中事件数量和模型诊断。内部复用已验证批次，不要求接入方手动合并多份错误数组。现有原始事件 API 保持兼容，不开放由调用者随意设置的“跳过安全校验”开关。

错误定位也应在同一批次保留源行/字节位置；目前冲突诊断里的 `inputIndex` 对应已过滤的有效事件序列，不等价于含空行/坏行文件的行号，不能直接拿来跳转编辑器。

**验收标准。**

- 坏行、无效 UTF-8、别名冲突、重放隔离、空行之后的错误，经过读文件到模型的组合调用后仍保留正确原始计数和定位。
- 两版 README 的未来示例只需一个清晰的组合入口或明确检查诊断；本轮不改它们。
- CLI/library 对同一输入的诊断语义一致；CLI 当前非零错误退出码不能退化。
- filtered 视图明确说明仅分析子集，不能把筛掉的终态当成原始运行确实没有终态。
- 增补现有 [坏行测试](../test/jsonl.test.js#L29) 到高层 API 的贯通断言，而不另搭完整服务。

**可行性与投入。** 1–2 工程日。高，属于现有数据结构的组合封装；同时为 F5 消除重复规范化提供明确入口，不需要更换持久化方案。

## F5：先消除确定的重复遍历，再考虑大日志功能

**证据。**

- [JSONL 第一次规范化](../src/jsonl.js#L40) 后，[collectEvents](../src/jsonl.js#L76) 再次规范化；CLI 随后 [构建索引](../bin/agent-trace.js#L60)，索引入口又 [collectEvents](../src/indexing.js#L7)。正常文件摘要路径对相同事件做了三次完整规范化，并保留多份数组/对象。
- [query](../src/indexing.js#L31) 每页都完整筛选候选集合，且在每个候选上重新 `Object.entries(filter)`。CLI [逐页收集全部事件](../bin/agent-trace.js#L69) 时重复做同一筛选，复杂度随候选数 N 与页数 P 相乘。
- [终态费用筛选](../src/model.js#L106) 对每条事件在线性数组 `terminalEventIds` 上 `includes`。大量终态同时间或缺时间时，终态集合 T 会很大，形成 O(N×T) 路径。

**本地操作次数复现，不是吞吐基准。**

| 合成输入 | 实际观察 |
| --- | --- |
| 1,000 个事件，同一筛选读 10 页 | 对同一 filter 调用 `Object.entries` 共 10,010 次，其中 10,000 次来自逐候选筛选 |
| 1,000 个不同 ID、相同时间戳的合法完成事件 | 终态 ID 数组被查找 1,000 次，对应 500,500 次从头逐项比较 |

以上计数通过一次性内存插桩取得，插桩在 `finally` 恢复；没有修改源码，也未生成大文件。未测得实际线上延迟、内存峰值或 50,000 事件耗时，因此不能宣称已经量化生产性能收益。

**影响。** 日志重放、列表翻页、CLI 全量摘要会做不必要的工作。异常但在大小限制内的高终态数量输入也可能显著阻塞进程。成本表现为 CPU、内存和用户等待，不是模型/API 费用。

**建议。**

- 基于 F4 的已验证批次，内部只规范化一次；公共 raw-input API 仍校验，查询仍返回防御性副本。
- 过滤条件先编译；同一不可变索引/筛选的分页复用匹配位置，或提供一次性迭代器。若缓存多个筛选，必须有有界淘汰，不能用无限缓存换速度。
- 无筛选的 CLI 摘要直接分析该批次，而不是为了收集全集绕一遍分页接口。
- 将终态 ID 的成员检测改为 `Set`；保留对外有序列表和费用未知/冲突语义。
- 不提高当前 32 MiB/50,000 条默认上限。先把现有限制内的路径做好。

**验收标准。**

- 相同筛选遍历所有页不再每页全量重建匹配集合；小样例用可数操作断言，不能只看一次快了多少毫秒。
- 终态费用筛选是线性成员查找，1,000/2,000 个同时间终态不出现比较次数近四倍增长。
- 对 1k/10k/50k 的有界合成数据记录耗时与峰值 RSS，公开环境与方法；只作为局部性能基线，不自动调用外部平台。
- 去重结果、错误保留、分页顺序、父子关系、工具配对和防御性复制与正确性修复后的基线一致。

**可行性与投入。** 1–2 工程日。高，主要是数据复用与查找算法，不需要 worker 集群、外部数据库或新增依赖。

## 两轮实施顺序

### 第一轮：证据语义一致性

范围固定为 F1、F2、F3，建议 2–4 工程日，具体以新增边界用例暴露的兼容性问题调整。

1. 先把上述合成复现转成定向回归，写清缺失范围、等价字段、冲突结果的预期。
2. 修正未知 run 的归属推断、规范化指纹与重放统计。
3. 统一冲突终态/费用的保守输出，保留原始证据，不篡改日志。
4. 统一执行一次相关单元测试和现有 demo；确认正常示例未破坏后再进入第二轮。

交付标准：日志不再因为等价字段布局被误删，未知范围/冲突记录不能无警告地升级为确定关系与成功。

### 第二轮：低成本、低出错率接入

范围固定为 F4、F5，建议 2–4 工程日；两项内部数据复用工作应合并设计，避免重复做一套缓存。

1. 提供保留 counts/issues/来源定位的组合入口，兼容现有函数。
2. 让 CLI 与公开示例走同一条路径，消除重复规范化；同步中英文示例的改动必须保持等价。
3. 优化分页匹配和终态集合查找，补小型操作次数测试与有界性能基线。
4. 发布前再统一跑本项目的 Node 内置测试、类型样例及 CLI，不能用只测新路径替代现有安全/UTF-8/配对回归。

交付标准：开发者可用一个明确入口获得带诊断的完整摘要；同一数据不会在多层重复整理，分页与摘要保持确定性。

附带的小检查：`package.json:14` 的 `files` 尚未显式包含 `README_EN.md`。将来制作包或发行附件时核对双语文件清单即可，本轮不进行 npm 发布，也不为此重写 README。

上述范围总计约 4–8 工程日，是熟悉本项目工程师的粗估，不包括外部框架支持、远程发布审批或未知日志格式迁移。

## 明确暂缓

- 不做托管看板、账户系统、云日志上传、实时 tail 服务或完整观测产品。
- 不把普通 JSONL 包装成防篡改审计，不引入签名链、账单结算或通用事实核查。
- 不扩展为 Orchestrator、工具执行器、失败自动重放器，不让日志里的命令获得执行权。
- 暂不批量适配 LangChain、OpenTelemetry 等外部格式；先用规范事件生产示例和一套稳定类型减少接入错误。有真实使用方、固定脱敏样例后再选择单个适配器。
- 暂不加长期持久索引、数据库、多进程并行、无上限日志或盲目增大资源阈值。
- 不自动 npm 发布、建立新的远端仓库或引入付费验收；发布授权与代码审查是不同步骤。
- 不取消冲突隔离、明确范围、缺失费用为未知、UTF-8 严格解码、终端控制字符处理等原有边界。

### 接入约定

- 优先 `analyzeCollectedTrace(trace)` / `createTraceIndex(trace)`，传入 `collectEvents` 或 `readTraceFile` 创建的完整对象，不传 `.events`、展开对象或 JSON 反序列化副本来冒充已校验批次。
- 原始事件入口 `summarizeTrace(events)` 和 `createTraceIndex(events)` 仍执行校验。低层 `modelForEvents` 的已排序/已去重/已规范化前置条件不变。
- `trace.events` 是语义规范事件；需要查看原始别名布局、冲突版本或源位置时读取 `trace.evidence`。批次属性每次读取返回副本；大型数据不要在循环中反复读取整个属性。
- `trace.evidence` 可含私密数据和工具参数。CLI 不直接输出它，也不会把无效金额字段中的任意对象泄漏到摘要。
- `README_EN.md` 已加入包文件清单；没有执行 npm 发布或打包上传。
