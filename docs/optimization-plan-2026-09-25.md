# TAgent 下一阶段优化计划

审查日期：2026-09-25。代码基线：`198b47d5297482ed5b159318bc89e606e9666d43`。

本文记录 2026-09-25 的代码审查基线和待实施计划，不是新增功能的完成声明。审查当时仅阅读源码、进行内存内的离线复现和整理文档，没有调用付费模型、执行搜索、重启服务或修改用户数据。之后的实施进展和未完成范围见 [总实施方案](../implementation_plan.md#下一轮优化入口)。

## 1. 结论与范围

项目不需要再重做一套 Agent 框架。现有常驻/任务 Agent、运行阶段、工具权限、交付核对、工作流、导入确认和会话能力已经构成产品主干。当前更高收益的工作是：减少无效等待与重复处理，使预算和完成状态准确，并让搜索结果能顺畅进入安全导入流程。

初心保持为：**非技术用户能稳定完成一次办公任务，看懂过程，低门槛配置能力。**

- TAgent 在当前任务继续，其他三个独立项目在各自原有任务审查和实施。
- 本轮提出计划，不默认开始代码改造，也不重新打开历史付费验收批次。
- 保留三栏布局、六类办公 Agent、雷达评分、Skill 拖拽和现有数据。
- 不增加 Desktop、Docker、自动 Session Merge、无人值守付费、多租户或无限 Agent 裂变。
- 不将三个独立包立刻替换进主应用。先稳定契约，再对一个实际使用点做兼容验证。

## 2. 主要发现

### T1 / P1：预算主要在返回后计费，缺少统一派发前预留

证据：`packages/tagent-core/src/agent-loop.ts:170` 先调用模型，`:196` 记账，`:218` 后进行成本治理。`orchestrator.ts:258` 的拆解、`:741` 的综合也未经过同一个请求预算预留器；`:278` 仅为包含 spawn 的计划分配任务额度；`:668` 在子 Agent 完成后才汇总其成本。

**影响**：低额度任务仍会发出请求；并行常驻 Agent 根据尚未归集的费用判断余额，无法把 `maxTotalCost` 当成派发硬边界。办公核对已有局部预算检查，但不能代替整个运行的共享账本。

**离线复现**：使用内存 Trace 和假 Provider，`maxCostPerTask=0` 时 Provider 仍被调用 1 次，记录合成费用 0.01 后才被拦截。没有外部请求或真实扣费。

**优化**：在模型派发边界统一检查额度、预留请求上限、结算回执，覆盖拆解、执行、综合、核对与有界修订。并发共享同一 run 账本；未知用量保持预留，不按零处理；预留最低交付/降级空间。

**边界**：本地估算和供应商实际账单不是同一件事。未知模型价格不自动派发；不能承诺仅靠本地 token 估算保证外部账单绝不超额。

### T2 / P1：检查点全量复制与队列等待放大长任务开销

证据：`packages/tagent-server/src/run-journal.ts:42` 每次 checkpoint 都复制完整状态并排队保存。`index.ts:614` 对文本和非终态工作流事件触发 checkpoint，`:619` 在 SSE 写出前等待保存队列。`workflow-index.ts:93` 追加数据时复制全部索引项并重写元数据。

**影响**：事件越多，重复序列化和写入越多；慢磁盘可能推迟页面看到进展。派生索引已有 32 个待办的保护，不应误称它完全没有上限，也不应删除此保护。

**离线复现**：200 条每条约 200 字符摘要的事件，产生 200 次保存调用，累计序列化 6,783,090 字节，最终检查点 67,397 字节，约 101 倍。该实验只测内存序列化量，不是实际磁盘耗时基准。

**优化**：先合并非关键进度快照，固定最多一个在写快照和一个待合并状态；对恢复关键事件强制持久化屏障。派生 Trace 索引批量追加并定期提交元数据，仍可从权威记录重建。

**不可破坏**：模型回执/费用、外部动作确认、最终结果必须可靠保存；不能为提高速度把回执落盘改成无保障的 fire-and-forget。停止与故障恢复不能重复工具动作。

### T3 / P1：导航刷新携带完整历史，保存改动重写全部工作区

证据：`packages/tagent-server/src/store.ts:123` 每次事务复制工作区集合并整份保存；`:344` 的 `listWorkspaces()` 返回完整嵌套对象。`index.ts:439` 直接用于工作区 API；`:542` 的消息接口没有分页。`packages/tagent-web/src/lib/conversations.ts:142` 刷新这些数据，`:323`、`:346` 在发送流程中再次刷新。

**影响**：导航只需要标题、时间和运行状态，却同时获取消息、Trace 和回执；历史累积会增加网络、解析、内存和保存负担。Trace 懒加载已经存在，但不能抵消完整消息接口携带的重复数据。

**离线复现**：一个合成会话中，工作区列表包含完整 5,000 字符正文及 200 条 Trace，序列化 72,863 字节。

**优化顺序**：先增加轻量导航 DTO、消息游标分页和按需读取 Trace/回执，限制非活动会话缓存；再按会话拆分持久化单元。保留旧数据读取和迁移回退，不把更换数据库作为前置条件。

### T4 / P1：办公核对是重型全量步骤，交付状态过度合并

证据：`packages/tagent-core/src/office-delivery.ts:348` 每次核对构建整份任务、材料、输出块和响应模板；`:363` 超容量则整份标记未核验；`:379` 截断或格式异常不能作为完整核对。`:410` 修订后再次完整核对。`orchestrator.ts:204` 将总体 `success` 直接绑定到核对是否通过。

**影响**：正文已生成仍可能长时间等待核对；较长交付更容易因完整检查容量不足而未核验。运行是否结束、正文是否生成、质量是否通过被混成一个成功标记，不利于用户判断下一步。

**优化**：先确定性检查格式、算式和显式约束，再对需要语义判断的块做有界核对。明确总 token、总次数和全局覆盖表；长文按稳定块标识处理，不通过少检查、删除内容来制造通过率。增加执行完成、交付可用性、核验状态三个语义，兼容旧 `success`。

**已存在而不重做**：单 Agent 直接交付已跳过重复综合；原稿、核对记录、有界一次修订和未知费用保留机制已有基础。

### T5 / P1：Discovery 提供方串行等待，慢源拖住快源

证据：`packages/tagent-server/src/discovery.ts:287` 依次等待 local、URL、curated、GitHub repo、GitHub code，再查询 npm、MCP Registry。`:444` 的三个文件名查询也顺序执行；每个 GitHub 查询有独立 12 秒超时。

**影响**：npm 或本地已有结果，界面仍可能等待 GitHub；多个提供方的等待时间叠加。本地直达 URL、GitHub 缓存/限流和真实错误状态已存在，问题不应再归结为“没有搜索源”。

**优化**：共享整体截止时间、请求取消和 2-3 个提供方的有界并发；按 provider 保留成功/失败/限流结果及稳定排序。先支持整体期限内的部分结果，确有需要再增加渐进返回，不强迫管理页引入复杂流协议。保留 GitHub 自身队列与退避。

**边界**：搜索不创建草稿；点击来源只填入导入源，预览仍不落盘、不执行。不能用更高并发绕过来源限流。

### T6 / P2：DAG 执行仍按整批等待，未利用空闲执行槽

证据：`packages/tagent-core/src/task-plan.ts` 的 `executeTaskPlan()` 对本批就绪任务 `Promise.allSettled` 后才更新结果集合，下一轮才识别新就绪的依赖任务。

**离线复现**：fast、slow 同时运行，child 仅依赖 fast；fast 在约 36ms 完成，child 却等 slow 在约 178ms 完成后才于 179ms 启动。延时由本地定时器模拟，不是模型性能测量。

**优化**：改为固定并发上限的 ready queue，依赖满足且有空槽就启动。仍等待运行中的任务完成取消清理，不能提前漏掉费用、结果或终态。该项优先级低于预算和数据热路径，避免为少量单 Agent 任务提前引入复杂调度。

### T7 / P1：同一句里的未知项或否定词会屏蔽明确约束

证据：`packages/tagent-core/src/office-grounding.ts:81` 要求整个任务句子不含 `uncertainSource` 才激活串行约束；`:87` 对报告整句应用 `correction` 过滤。

**离线复现**：任务为“严格串行。”、报告为“建议并行执行。”时会正确报错；任务改成“严格串行，负责人未知。”后，同一报告返回空检查列表。任务仍为“严格串行。”，报告为“不要并行设计和开发；建议并行开发和测试。”时也返回空检查列表。

**影响**：真实任务很常见的“已知约束 + 未知人员”组合，会让确定性兜底漏掉明确冲突。这不等于后续模型核对一定通过，但不能依赖模型补救本地已有规则本应识别的情况。

**优化**：使用保留原文位置的局部子句/匹配区间，让未知、否定、假设只影响对应约束或建议。先添加成对正反例，再收紧作用域；不升级为通用自然语言推理器。与 Evidence-Bound Review 共享用例约定，不直接用其未修复实现替换 Core。

## 3. 下一轮实施顺序

下列为单人有效工程日估计，不含等待外部服务、付费验收或工作中断，不是交付日期承诺。每一项可独立提交和回退。

| 批次 | 工作项 | 用户收益 | 估计 | 可行性与依赖 |
| --- | --- | --- | --- | --- |
| A0 | 明确串行等约束的局部作用域 | 已知工期/依赖不因未知负责人失效 | 1-2 日 | 高；先修上述确定性漏报，不做宽泛语义扩展 |
| A1 | 统一模型派发预算预留与回执结算 | 额度不足不继续花费，避免并行超派发 | 2-3 日 | 中等；复用现有 CostTracker/回执，先做单 run，不做全账户账单系统 |
| A2 | 检查点合并、Trace 批量索引 | 进度更及时，长任务少做重复 IO | 2-3 日 | 中等；恢复语义不变，先有故障夹具再切写入策略 |
| A3 | 导航轻量 DTO、历史消息分页 | 会话增多后仍能快速打开和切换 | 2-3 日 | 中等；先改读取，持久化拆分单列后续，不一口气迁移 |
| B1 | Discovery 有界并发、截止时间、部分结果 | 慢源不再让所有结果一起等待 | 1-2 日 | 高；复用 provider/cache/status，不更换搜索服务 |
| B2 | 正文、执行、核验三态分离 | 有正文时能阅读使用，未核验原因清楚 | 1-2 日 | 高；兼容旧消息，不能把未核验显示为通过 |
| B3 | 分块且有界的核对策略 | 长文不因单次核对过大反复超时 | 3-4 日 | 中等；依赖 A1 和覆盖率契约，采用可回退开关 |
| C1 | 固定六类任务输入/交付合同与失败样例 | 普通用户知道要提供什么、能得到什么 | 2-3 日 | 高；复用现有任务模板与 Agent，不新增角色；先研究/项目再复制 |
| C2 | 就绪队列调度 | 多 Agent 依赖任务减少空等 | 1-2 日 | 中等；依赖 A1，基线确认有收益再启用 |

推荐先完成 A，约 7-11 个工程日；A0 与 A1 都是首批正确性修复，先于性能重构。完成后根据本地延时/数据量基线调整 B。C 不作为前两批发布前置条件。所有工作不要求新增基础设施或更贵模型。

### C1 的具体交付约定

- 研究：区分日期已知/未知/旧资料，来源可定位，证据不足直接标明。
- 文档：正文结构、篇幅、引用和现有导出保持一致，不以内部交接摘要替代正文。
- 数据：原始输入、口径、缺失值、计算步骤与异常说明可回查。
- 项目：严格使用给定工期与依赖；未知负责人不扩大成全部岗位缺失。
- 沟通：收件对象、目的、语气与可直接编辑的稿件；不登录邮箱、不自动发送。
- 汇报：页面级大纲、关键证据、讲稿要点；不承诺本轮生成复杂 PPT 视觉成品。

Benchmark 优先复用这些已完成任务的 Trace 和人工标注失败样例，呈现通过项、未覆盖项和主要短板；不自动另跑大量付费测试，也不把静态估算改名为实测。

## 4. 验收标准与停止条件

先用固定离线夹具验收有改动的模块，每批收尾一次相关集成回归；最后统一验证一次，不在每个小修改后重复全量构建和付费调研。

| 项目 | 必须满足 |
| --- | --- |
| 约束 | 已知串行与未知负责人共句时仍激活检查；混合否定/肯定建议逐项判断；真正未来获批的替代方案与引用例子不误报 |
| 预算 | 0/不足/无价格时模型派发为 0；并发预留总额不超本地授权额度；未知回执不释放成可再次使用余额；有非空降级输出 |
| 保存 | 合并队列大小有上限；关键回执、最终结果故障恢复一致；重复调用不重放已执行工具；1,000/5,000 事件夹具下记录写次数和字节量，与当前基线比较 |
| 历史 | 导航响应不含正文/完整 Trace/原始核对回执；分页无重无漏；中文/emoji、Fork/Diff、取消后刷新保持正确 |
| 搜索 | 模拟慢 GitHub、快 npm 时在整体期限内返回快源结果；取消终止剩余请求；失败来源清楚；搜索与预览均无意外写入/执行 |
| 核对 | 原文、块标识和引用稳定；局部通过不能冒充全篇通过；明确失败、未覆盖和未知；总核对成本/次数受 A1 约束 |
| 调度 | child 在依赖完成且槽位可用时启动，无须等待无关 sibling；并发数量受限；取消清理、最终事件和费用不丢失 |
| 用户体验 | 不增加完成普通任务的必填项；正文不被侧栏遮挡；简单任务可读结果更早出现；保留现有安全确认步骤 |

性能目标先记录修改前基线，再在同机同数据上比较首条进展时间、正文就绪时间、核对附加耗时、请求次数、峰值内存、写入字节和导航响应大小。目标是明确减少工作量，不在本次审查里虚构“提升百分比”。

真实内容质量最后才做少量、明确授权的验收；离线模拟和工程门槛通过不代表模型内容已达到金标准。达到上述范围即收尾，不以仍可扩展为理由无限继续。

## 5. 三个独立项目的协作边界

| 项目 | 负责的原任务 | 当前协作方式 |
| --- | --- | --- |
| agent-trace-kit | 开源提取：Agent Trace Kit | 独立审查 Trace 写入/查询/恢复和包可用性 |
| approval-first-import | 开源提取：Approval-First Import | 独立审查预览确认、持久化、一致性和集成成本 |
| evidence-bound-review | 开源提取：Evidence-Bound Review | 独立审查证据定位、确定性检查、边界与测试 |

三个原有任务均已完成审查，分别在自己的独立仓库保存 `docs/optimization-plan-2026-09-25.md`，没有交叉修改产品代码。汇总如下；详细证据、复现、源文件行号和验收标准以各项目文档为准。

| 项目 | 优先修复 | 后续效率/实用性工作 | 建议投入 |
| --- | --- | --- | --- |
| agent-trace-kit | P1：未知 run 不推导确定父子/成功；等价别名误判冲突；矛盾终态/费用明确诊断 | 保留原始校验诊断的组合入口；一次规范化；复用分页筛选；Set 替代终态数组查找 | 两轮共 4-8 工程日 |
| approval-first-import | 最高优先级：脱敏反复替换自己生成的占位符，极小输入放大；P1：合法上限候选不能原样确认、审计挂起不释放确认状态 | 非递归有界脱敏；统一包/信封预算；审计期限；文件目录冲突检查；一个原子保存/幂等回执宿主示例 | 三轮共约 6-11.5 工程日 |
| evidence-bound-review | P1：整句未知/未来/否定词导致串行漏报；重复引用反复分段和扫描 | 保留偏移的局部规则；单次调用缓存；按单位/来源绑定关系；安全整数处理；结构化输入错误 | 三轮共 3.5-7.5 工程日 |

子项目的有限离线复现包括：导入库一个字符正文在12个重复短 env 值下变为36,856字符；Trace 的 `blocked + success:true` 记录仍被汇总为成功；证据库同一份材料的16条重复引用比1条多做大量相同扫描。它们是合成问题证据，不是生产事故声明，也不是修复完成。

总体顺序：先修导入库的预览资源边界，以及 TAgent 的预算/明确约束；另外两个项目并行修证据语义。随后再做各自性能与接入示例。三个小库目前不是主应用运行依赖，不能把它们的缺陷直接视为主应用同样存在，也不能因修好小库就宣布主应用同步修复；本轮已另行复现的 T7 除外。

先处理正确性，再优化性能和集成体验；本线程只汇总依赖和采用顺序。`opensource/` 嵌入副本与独立仓库的同步放在明确发布点进行，不做双向自动覆盖。
